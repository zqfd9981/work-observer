# 原始愿景与当前成熟度复核

2026-11-19。依据原《长期规划》《长期架构设计》与当前代码复核。0.4.0应定位为**功能覆盖较广、可本地试用与演示的Alpha工程版本**，不是原始完整愿景已经实现，也没有足够证据认定生产就绪。此前G6–G9的“完成”只说明选定实现和局部验收完成，不能作为整个产品完成度。

## 已有证据能证明什么

255项测试主要证明隔离条件下的数据、权限、预算、恢复与业务服务机制；少量真实模型调用证明指定样例能够跑通。它们不证明开放研究问题的普遍正确率、长期自治能力、全市场召回或线上稳定性。50个API路径和19张业务表也不能作为业务成熟度指标。

实现速度来自复用已存在的采集/档案/CLI/页面底座和对独立子任务并行编码；真实多日运行、独立语义评测和长期知识积累不能由并行编码替代。

## 应如何衡量剩余工作

不能用“接口做了多少”给出可信总百分比，也不能把剩余工作说成最后一点打磨。当前底座与主流程覆盖较多，但**研究能力深度、知识演进、真实质量评测与长期运行**仍是核心建设工作。

后续应按业务验收推进，而非继续堆接口：

1. 建立冻结的真实研究任务与人工标注，分别评估检索、引用语义支持、未知处理、画像遗漏、用量及最终问题是否回答；保留独立验收样本。
2. 用已有静态/人工资料完成持久调查计划与缺口驱动的多阶段研究；明确停止条件、人审等待、后续任务及跨次汇总。无需恢复招聘来源即可研发。
3. 将岗位与公开业务资料组成统一证据库，建立可版本化的领域定义、任务能力关系、反例及冲突处理，让新研究能真正修正旧认识。
4. 在同一真实评测上验证一种研究或检索策略改进，完成配对、证据不足、人工审核、限量应用和质量退化回退，而非只跑模拟6题。
5. 在可用授权资料上进行连续使用和部署环境验收；招聘源恢复另定目标，始终保持当前暂停。

后续某项能称“完成”的条件，应同时说明：可操作入口、业务深度、真实或隔离证据、未覆盖部分及其影响。前一轮已实现代码和数据保护结果保留，不因本次更正而否认其工程价值。
