# 0.14 项目内复核补查与阶段验收

2026-11-19，单用户本地Alpha，持续目标保持active。本轮把0.13的显式拒绝反馈接入持久研究项目；不新增真实模型调用，不把工程验证当作研究质量提升。最近真实证据仍是0.13的5调用补查：资格强度仍错，Agent拒绝及原运行保持。

## 从复核安排项目内补查

先在研究质量页逐项保存拒绝复核，再从该页进入原项目。项目步骤显示“参考拒绝复核，安排项目内补查”，保留人类/Agent来源、固定复核ID及剩余可预留预算。填写说明，可先仅整理反馈与原文，或明确取消离线选项安排模型调查。保存只入队；点击项目的“继续可执行步骤”或明确运行队列才执行。

补查沿用原问题、岗位集合、范围版本和完成条件；原结果、审核、实际调用与整轮预留不改。无需假装材料已变化，也不能从普通研究入口带项目编号另开额度。执行须对应本项目已经领取的步骤，检查替代回链、复核ID、范围和调用/时间预算。继续保留项目、worker批次和日常流程上层预留，不开启公开补查。

接口新增`POST /api/projects/{id}/steps/{step_id}/repair`，输入`revision`、`review_id`、`note`和可选`offline/max_calls/timeout`。CLI使用同一业务服务：

```powershell
uv run --locked work-observer product projects repair --id <原项目ID> --file <补查输入JSON> --db <工作区数据库>
uv run --locked work-observer product projects run --id <原项目ID> --db <工作区数据库>
```

JSON还需`step_id`，其余字段与接口一致；`offline`默认true，必须明确设false才安排模型调用。原轮预留5次但实际只用3次时，这5次仍保留；后续轮最多只能使用项目尚未预留的额度，不能把未用2次悄悄转给别轮。

## 版本、等待与重新安排

重复保存同一计划返回原步骤；复核变化后，旧计划不能静默换版本。执行前已变化会在调用模型前停止，中途变化会保留已消耗调用并停止。已领取失败轮仍保留完整预留；可在其步骤上明确按最新复核另建一轮，受剩余总预算和轮数限制。未领取的旧计划也可显式被新复核计划接替，仍保留历史。

离线反馈预览完成后，可以明确转为模型补查，保留同一复核来源，累计原项目预算。若材料或口径已变化，应走更新资料重查，清除旧反馈的执行绑定，重新调查当前资料。中断恢复沿用原检查点、复核版本和剩余调用，不追加整轮额度。

被拒绝的前置结果不释放后续汇总；执行完成也只进入等待核对。新补查接受后，前置关系才沿替代链接续。存在当前拒绝复核时，项目“接受本步”不能绕过该拒绝；须先补查，或在质量页完成新的逐项核对。没有逐项质量审核的项目接受仍只表示项目步骤的明确核对，不冒充六维业务批准。

## 防止旧答案回流

反馈只包含有界诊断。项目上下文排除被拒绝的旧结果及其事实派生；反馈新轮还会排除直接或经记忆、研究、领域关系间接引用旧答案的背景。原始岗位仍可重读；对记忆的排除只影响本轮选择，不把Agent拒绝变成用户撤回，也不改变原记忆状态。

隐私回链`feedback_from`继续独立于事实继承`continued_from`：新结果重新核对原文后，可以成为后续研究的上下文，不因仅参考旧诊断而自动继承被拒绝的事实。遗忘个人记忆或整个项目仍清除相关补查、未执行计划说明、检查点、报告、审核与通知；独立备份保持独立，恢复后可在该副本中另行遗忘。

显式反馈方法登记v7，指纹覆盖反馈、项目执行与依赖选择实现；旧v6运行和评语不回填。普通标准提示及工具合同v5摘要仍为`39a1ac28…dff24`，没有自动启用研究候选。来源分项共享引擎登记v10，仅兼容工程验证，没有新增真实质量证据。
