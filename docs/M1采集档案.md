## 数据与归属

采用 SQLite、SQLAlchemy 2.0.58、Alembic 1.20.1，均已在 uv 锁文件中锁定。新增迁移 `d3cff3ef944a`，`db-init` 显式创建或升级结构，不在每次业务运行时静默修改表。业务程序检查表和迁移版本；迁移与模型一致性经测试验证。

| 表 | 当前保存的内容 |
| --- | --- |
| `watchsets` | 名称、不可变配置、配置指纹和版本；每次运行绑定具体版本 |
| `task_runs` | 本次手动执行的类型、开始与结束时间和状态；尚无调度、租约或恢复执行 |
| `collection_runs` | 来源模式、观察版本、逐页和逐详情进度、错误、调用预算与覆盖限制 |
| `jobs` | 内部 ID、来源、来源岗位 ID、首次和最近观察时间；不以岗位标题合并身份 |
| `source_documents` | 每次请求的参数、原始响应路径和 SHA-256、采集与归档时间、回放来源信息 |
| `job_snapshots` | 列表或详情的岗位内容、指纹规则版本、内容指纹和首份来源文档 |
| `job_observations` | 每次运行、页码和位置、岗位与快照、这次的来源文档及访问上下文 |

数据库有来源加岗位 ID 的唯一约束；快照按岗位、类型、规则版本和内容指纹唯一；观察按本次运行、岗位、类型和页码唯一，外键开启。SQLite 使用 WAL 和有限锁等待，业务写入是短事务。网络请求时不保持业务事务；测试检查请求期间没有占用业务连接。当前仍只面向单个手动执行者，不支持并发采集调度。

岗位 ID 是目前来源身份候选；本次相邻两次真实调用一致，不能据此证明跨日、换登录会话或来源重新发布后也稳定。`security_id`、`lid`、岗位链接仅作为这次观察的访问上下文，保存在内部，不作为岗位身份或内容变化。

## 原始响应、快照与观察

原始 MCP 响应保存到 `data/raw/m1/<指纹前两位>/<SHA-256>.json`，在保存前移除认证字段及已知密钥；其余来源字段和缺失值不补造。保存的是完整 MCP 响应的规范 JSON 序列化，不是网站底层 HTTP 抓包。指纹针对实际 UTF-8 文件字节，临时文件落盘后原子替换。同响应可复用文件，但每次请求仍建立独立来源文档；已有文件损坏时明确失败，不覆盖损坏证据。

岗位内容指纹使用 `job-content-v1`，保留标题、企业、薪资、地点、职责、要求和标签等业务字段，排除访问标识、招聘者活跃度、沟通状态和匹配分数。未纳入当前规则的新字段仍在原始响应中，后续纳入指纹需变更规则版本。

- 相同岗位、相同内容：复用快照，新增本次观察与来源引用。
- 相同岗位、详情变化：保存新详情快照，旧快照及观察保留。内容从 A 变为 B 再回到 A 时复用已有 A 内容，观察顺序仍保留。
- 同标题、不同来源 ID：保留不同岗位，不自动合并。
- 列表与详情：分别保存，不用详情中的空 `city` 或空 `skills` 覆盖列表字段。
- 失败页：保留错误或客户端失败记录，数量为 `null`。仅来源明确成功且数组为空时，才保存成功的零结果页。

不补造来源发布时间；`observed_at` 是获得响应的时间，`processed_at` 是处理时间。搜索暂时没出现的旧岗位不会被删除或判定撤招。尚未进行公司归一化、薪资解析、岗位分类或跨 ID 的相似招聘合并。

## 来源与执行预算

`MCPSource` 复用 M0 的独立 stdio 客户端，每次启动重新发现工具、校验实际参数结构，只允许 `boss_search` 和 `boss_detail`。M1 不调用模型或公开搜索，不发送招聘消息或投递，不修改 BOSS 的浏览器和认证配置。

`configs/watchsets.toml` 的 `ai-dev` 为上海、`Agent`、固定观察组，默认最多一页、列表中前两个唯一岗位的详情、三次业务调用尝试。硬上限分别为五页、十条详情、十五次业务尝试；请求预算同时约束列表和详情。参数校验失败等尝试同样消耗本次预算，指标不是网站底层 HTTP 请求计数，也不代表绕过连接器缓存。工具发现与握手不计入业务取样预算。

来源仍有下一页而达到页数或请求预算时，`list_coverage_limited=true`；详情只覆盖选定样本时，`detail_coverage_limited=true`。预算内已请求步骤均成功可记 `success`，同时保留覆盖有限，不能把来源 `total=15` 当市场总量。本阶段按有限样本验证档案，详情轮换、新岗位优先及周期复查不在此实现。

`success`、`partial`、`failed`、`needs_auth` 与任务表同步。已经保存的有效页或详情不会因后续失败而撤销；后续页失败会停止翻页。登录、浏览器不可用、平台风险、限流、预算锁等错误停止当前来源操作，不切换通道或自动重试。普通详情不存在可记录后继续剩余的有限详情请求。

进程被直接终止时可能留下 `running` 状态，本阶段不自动抢占或续跑；每页与详情已独立提交的内容仍保留。M2 才处理租约、崩溃后的运行状态与断点恢复。文件已保存但数据库提交失败可能留下孤立原始文件，M1 保留它们供核查，不进行自动清理。

## 真实样例回放

`replay-m0` 只读取指定 M0 目录中的真实调用声明、招聘通过状态、原始响应和请求文件，逐文件校验 M0 清单中的 SHA-256。不能伪造未记录的页、参数或详情，文件不匹配即失败。清单校验用于发现本地文件变化，不是平台数字签名。

回放模式是 `replay`，无平台调用。因为 M0 未逐份记录响应时间，观察时间明确使用原 M0 批次结束时间，并记录精度说明；不会使用回放时间伪装新的市场观察。每次回放会建立新的处理运行与关联观察，其原采集时间不变，不能作为多个独立市场样本。

实时库默认 `data/app.db`；回放默认 `data/replay.db`。CLI 禁止回放写入配置的实时库，Repository 也禁止一个已有运行的数据库混合 `live` 与 `replay`。模拟测试只运行于 pytest 临时目录，不进入两种真实资料库。

## 命令入口

在项目根目录运行：

```powershell
$env:PYTHONUTF8 = "1"
uv sync --locked
uv run --locked work-observer db-init
uv run --locked work-observer collect --watchset ai-dev
uv run --locked work-observer runs
uv run --locked work-observer db-stats
uv run --locked work-observer jobs
uv run --locked work-observer job --id <内部岗位ID>
uv run --locked work-observer history --job-id <内部岗位ID>
```

数据库路径可以用 `--db` 或环境变量 `WO_DATABASE_PATH` 指定；原始文件目录由 `WO_RAW_DIRECTORY` 指定。默认都在被 Git 忽略的 `data` 中。`--watchsets` 可以指定观察配置文件。`job` 分别返回列表内容和详情全文，`history` 返回每次观察、快照和原始文件引用；两者不输出访问上下文或招聘者姓名。运行摘要不输出平台岗位 ID、访问标识、来源错误全文或密钥。

回放示例：

```powershell
uv run --locked work-observer db-init --db data/replay.db
uv run --locked work-observer replay-m0 --bundle data/raw/m0/20261117T090846Z_57ff5988 --db data/replay.db
uv run --locked work-observer replay-m0 --bundle data/raw/m0/20261117T090846Z_57ff5988 --db data/replay.db
uv run --locked work-observer db-stats --db data/replay.db
```

缺少配置、表未初始化、业务失败、部分成功或需要认证时返回非零退出码。CLI 不自动登录，不要求为了测试失败场景而反复人工恢复。

## M2 前仍需解决

用户要求定时运行不需要人工开浏览器、导入登录态、确认继续或处理验证码。**本阶段没有解决这个条件，也没有通过无人值守验收。**两次实时采集依赖原有已登录的专用浏览器会话，没有额外要求用户重新登录，但这不证明主机重启、浏览器关闭或认证过期后可自动恢复。

M2 开始或启用前需明确适合无人操作的来源与认证机制；如现有 BOSS 无法满足，重新选择主来源。随后再实现调度、运行租约、断点、并发约束、认证异常处理和有限详情复查。业务库、归档和来源合同可以保留，不需要将存储绑定到当前浏览器方案。
