## 已实现的闭环

`work_observer.quality` 只读来源数据库，用 SQLite backup API 冻结独立副本。冻结时验证每份正文所属快照、原始文件 SHA 与正文一致性；保存资料、版本、正文 SHA 和来源类型。缺正文、未知发布时间仍明确为空。冻结库、问题原文与逐例结果都是本机私有资料，不提交仓库。

问题先划分为 development 和 holdout，并为相关岗位填写可核对的原文锚点及判断理由。问题、语料、门槛和候选配置均锁定摘要；候选须先经过开发集登记，才能使用预留验收集。每套题只允许一次 holdout 尝试，失败也保留登记，不能调参后反复拿同一验收集证明改善。验收失败后应建立新的独立任务，而非复制旧问题换编号。

配对评测在同一冻结库调用实际 `RetrievalService`，分别记录宏平均召回、精确率、空相关集是否误召回、关键退化、全文片段位置、来源版本与上下文预算。它不写正式库、不启用策略、不调用网络或模型。候选配置与检索评测的通过仅产生审核建议；方法应用及实际质量回退还需与产品策略流程接通。

标签来源明确区分 `human` 与 `agent_assisted`。默认是 Agent 草案；即便指标上升，未经人类审核仍返回 `insufficient`。程序不会把开发 Agent 的阅读判断包装成人工金标准，也不把同一语料上的新问题称为未见企业的独立样本。

## 操作

```powershell
uv run --locked python -m work_observer.quality freeze data/app.db data/quality/my-baseline
uv run --locked python -m work_observer.quality lock data/quality/my-baseline data/quality/cases.json
uv run --locked python -m work_observer.quality evaluate data/quality/my-baseline data/quality/aliases.json data/quality/development.json
uv run --locked python -m work_observer.quality evaluate data/quality/my-baseline data/quality/aliases.json data/quality/holdout.json --phase holdout
```

`freeze` 的目标目录必须不存在；`lock` 和输出文件不静默覆盖。只有人类明确核对标签后，才在新的锁定流程中使用 `--label-origin human --reviewer <审核者>`。不得仅为得到 accepted 而更改来源标记。

每题字段为 `id`、`split`、`question`、`terms`、`relevant`、`critical`、`notes`。`relevant` 是由 `job_id`、逐字 `quote`、`reason` 组成的数组；明确无相关证据可为空数组。空相关集不表示全市场不存在，也不能把缺失正文记为没有要求。

## 业务语义审核

使用研究结果 JSON 和六维判断 JSON 提交审核：

```powershell
uv run --locked python -m work_observer.quality review data/quality/my-baseline D01 data/quality/result.json data/quality/judgments.json data/quality/review.json --reviewer <审核者>
```

判断 JSON 必须同时包含以下六个维度。每维有 `rating`（pass/fail/unknown/not_applicable）、`reason` 与 `claim_indexes`（从零开始）。引用语义维度必须覆盖全部 claim。程序另核对每条引用的冻结来源、文档 SHA、精确位置与原文，伪造片段、空引用、范围外引用不能得到通过。

| 维度 | 审核问题 |
| --- | --- |
| `citation_semantics` | 所引片段是否支持判断的主体、范围、强度；综合与推测是否标明？ |
| `requirement_classification` | 必备、加分、未明确是否符合原文；并列可选语言是否被误说为全部必备？ |
| `profile_coverage` | 任务、交付物、责任、能力、工具是否有重要遗漏；未说明的内容是否保持未知？ |
| `unknown_handling` | 缺正文、未明确要求、来源时间未知与当前范围之外是否被正确处理？ |
| `counterexamples` | 是否保留不支持统一解释的样本，避免用个别岗位外推全市场？ |
| `question_answered` | 结果是否实际回答原问题，完成条件是否满足，未解决部分是否明确？ |

这六维是审核者提交的业务判断，不是程序独立证明。Agent 协助审核须用 `--reviewer-kind agent_assisted`，不会产出 `reviewed_pass`。审核同时保留结果摘要、模型调用、耗时、提供方 usage；费用未知则为空。

## 本次实际证据

本机 `data/quality-baseline-20261119-v1/` 已通过上述独立命令执行：正式库只读冻结为 15 个岗位、7 份完整正文、8 份缺正文；7 份原始文件及正文快照完整性核对通过。冻结题集有 4 道开发题、4 道预留验收题，均来自真实既有资料，标签为开发 Agent 阅读后给出的原文锚点草案，状态 `pending_human`。

使用固定的记忆中英词与长对话/多轮交互别名，在同一冻结资料上实际调用现有检索器：

| 分区 | 基线宏平均召回 | 候选宏平均召回 | 候选宏平均精确率 | 评测结论 |
| --- | --- | --- | --- | --- |
| 开发 4 题 | 0.6875 | 1.0 | 1.0 | insufficient，等待人类核对标签 |
| 预留验收 4 题 | 0.8333 | 1.0 | 1.0 | insufficient，等待人类核对标签 |

预留验收包含一题正文没有博士明确要求的空相关集；该题记录正确未召回，不纳入召回均值。候选没有关键退化，来源版本及 7000 字上下文预算护栏通过，外部调用为零，任何策略均未启用。以上是**真实资料上、Agent 草案标签下的检索效果**，不是人类独立验收，也没有测得端到端研究成功率、语义支持率或长期改善。8 题较少且共享7份语料，不能推广为市场效果。预留集已经消耗，不再用于调参验收。

隔离机制测试覆盖冻结篡改、标签锚点和分区、实际检索配对、候选锁定及单次验收、逐 claim 语义送审和伪造引用拒绝。它们使用明确合成资料，只证明机制。

## 产品内核对入口

新增 `GET /api/quality` 安全概览与 `GET /api/quality/runs/{id}` 送审包。包中逐条展示判断、原文、来源/版本/位置、必备/加分/未明确、原研究缺口和调用/耗时。页面片段与脚本位于 `api/assets/quality.html`、`quality.js`，主工作台接入后使用“研究质量核对”入口。概览只显示固定命名冻结基线的安全统计；API不接受任意文件路径、问题集、候选配置或门槛变更。

`POST /api/quality/runs/{id}/reviews` 提交六维判断和每条 claim 的语义支持、要求性质、理由；默认待核对。人工批准须全部 claim 已核对支持、要求性质正确，六维满足或有明确不适用说明，引用语义和问题回答两维必须满足。存在来源、记忆或方法变化时不能批准。Agent协助评审可保存为待审或拒绝，不能代替人工批准。

审核保存于独立 `checkpoints.db` 的 `quality_reviews` 表，按业务库 namespace 隔离，不复制原报告或证据正文。每次提交比较结果 SHA，旧页面不能给已变更结果盖章。完全相同的重复提交幂等。拒绝时以审核说明生成一个关联待补查项，沿现有收件箱流程衔接下一次研究；不会自动调用模型或改研究策略。关联研究遗忘后，审核服务提供 `invalidate(run_ids)` 擦除所有审核自由文本，只保留最少失效元数据，旧审核包不能重新提交。完整备份已包含检查点文件，因此同文件中的审核记录随检查点备份。

新增10项隔离测试均通过，涵盖重新打开检查点后读取、不同业务库隔离、结果变更拒收、来源变更重新核对、Agent不能批准、未知不能批准、重复拒绝只建一条后续问题，以及遗忘后自由文本清理与旧包拒收。新命令、业务服务、API和JS静态检查通过。页面实际视觉操作验收、真实模型结果的独立人审、候选策略有限应用/回退联动和连续运行质量仍需分别完成，不能把新增审核入口称为已证明长期质量改善。

## 真实多轮任务的独立 Agent 业务复核

本轮项目隔离库完成两轮真实模型调查后，另由开发 Agent 离线逐条阅读两份完整原文并复核全部14条判断，额外网络/模型调用为零。审核明确保存为 `agent_assisted`，两轮均为 `rejected`，不是人类金标准。私有证据保存在 `data/project-verification/quality-agent-review-round-1.json` 和 `quality-agent-review-round-2.json`；审核前后原研究记录摘要相同，没有修改原始回答来冒充一次成功。

第一轮9条事实主干均有本地原文依据，但3条的要求性质需要统一规则：同一个任职资格段中的陈述分别被当作必备和未明确。第二轮5条中4条的本条引用足够；另一条用单侧原文作跨岗位比较，遗漏另一岗位引用，需标为综合并同时引用两侧。第二轮另有一条混合了资格陈述与明确优先项，整体却标未明确，且没有解释与前轮分类的变化。

两轮都正确保留合同主体、来源发布时间、生产上线/值守/事故责任未知，没有拿入库时间代替来源发布时间，没有外推到范围外岗位。第二轮重新读取两份原文，提供具体任务差异，没有把旧结论转成独立证据。仍发现连续性限制：当时上下文仅取前轮前4条判断，后续重要的资格与优先项被裁掉，即便仍有上下文预算，无法证明完整续接了上轮所有重要结论。

这些问题已用相同审核服务落库，并各生成关联待补查项。来源SHA、引用位置、记忆与方法版本的可计算审计均通过，业务审核仍拒绝，说明新增质量入口确实能记录结构检查无法证明的缺陷。后续应先明确稳定的要求性质口径、避免按列表前几条丢失重要上下文、完善跨源综合引用，再用新问题和冻结资料验证；不能重用已消耗的预留题或改写原回答来宣称修复验收成功。

## 同题方法候选的开发回归

随后明确了稳定口径：任职资格中明确要求具备、熟悉、掌握、精通等视为岗位要求 `required`；明确优先为 `preferred`；没有个人资格措辞的任务或项目组件为 `unspecified`。这表示招聘原文要求，不等同于现实录用的一票否决。

同一问题、两个岗位及来源快照下再次执行候选方法，保留原回答。开发 Agent 按同一新口径分别复核基线与候选：基线9条事实主干均有依据，8条性质正确，1条好奇心资格要求被错标未明确；候选11条事实主干均有依据，10条性质正确，1条在required工具要求中混入preferred解释，仍需拆分。候选的跨源综合使用双引用、资格要求与任务组件的区分更明确，但尚不足以认定方法已通过。
