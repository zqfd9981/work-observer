# 登录资料与安全令牌自动更新验证

验证日期：2026 年 11 月 17 日。用户接受程序短暂启动后台浏览器，但不接受每次任务要求人工开浏览器、扫码或输入确认。本次只验证连接与认证能力，不创建定时任务，不进入 M2。

## 实际结论

**已真实通过一次完整链路：已有加密登录资料 → 自动后台更新安全令牌 → 加密保存 → 新进程读取 → 独立 HTTP 查询岗位状态。** 全程没有人工输入，没有连接用户原本打开的浏览器，没有重新扫码。

最早一次诊断因本地回调参数错误，在启动后台浏览器和请求网站前退出；修正后才进行上表的真实后台更新。该失败报告单独保留，不计为更新或连接成功。

## Cookie 与安全令牌分别证明了什么

1. **安全令牌自动更新已通过。** 本次从旧副本自动取得不同且实际可用于 HTTP 详情的新令牌，不依靠人工刷新网页或从现有浏览器复制。
2. **HTTP 返回的 Cookie 可自动接收、加密保存。** 观察到的是 `__zp_sname__`、`__zp_sseed__`、`__zp_sts__`。这两次 HTTP 响应没有改变主要登录 Cookie `wt2`，也没有改变 `__zp_stoken__`；不能将这些 Cookie 更新解释为账号登录期限已被延长。
3. **主要登录 Cookie 本轮沿用成功。** 后台更新前后 `wt2` 相同，仍支持真实查询。本次没有发生账号登录 Cookie 自然到期，不能声称已验证账号到期后可免扫码重新登录。

当前 SDK 的纯 `httpx-only` 刷新策略不会启动浏览器；现有静默更新实现依赖浏览器运行官方页面。本轮验证的是用户已接受的“程序自动短暂运行后台浏览器”，不是全程不运行浏览器。

原 `AuthManager.force_refresh` 实现只覆盖顶层 `stoken`，未同步 Cookie 字典内的旧值。本次诊断在保存候选资料时同步这两个位置，再通过真实详情查询验证，避免重载凭据后两处不同。这个同步仅在本地诊断脚本中完成，尚未修改外部连接器或接入业务采集。

## 对后续定时运行的意义与边界

可以继续采用以下正常运行路径：

> 任务启动 → 从加密存储读取已有登录资料 → 自动后台更新一次安全令牌 → 关闭后台浏览器 → 用 HTTP 查询本次岗位 → 接收并保存有效 Cookie 更新。

后台更新放在一次采集任务的开始，不需要为每个岗位打开网页，不需要模型逐条操作浏览器。上面的单次链路已经实际执行；尚未实现调度、长期 worker 或自动认证管理模块。

**本次仍不等于“只登录一次，以后永不需要人”。** 尚未验证：

- 连续多天运行、主机重启后的实际登录持续性；本次仅验证独立进程重启、已有保存资料和单次后台浏览器启动。
- 主要登录 Cookie 自然到期或被平台撤销后的恢复；现有实现没有在本次证明可自动重新登录。
- 平台要求扫码、短信或安全验证时的无人处理能力。当前来源规则仍要求遇到此类风险停止，不能将主动更新变成风险后的循环重试。
- 三天、七天以上的岗位访问参数有效期，以及不同岗位的普遍有效性。本轮仅增加了一个约 32.4 小时的跨日成功样例。

下一阶段应先将这个主动更新流程做成有界的认证适配器，再安排真实跨日观察，并将认证失败与岗位关闭分别记录。当前已有 MCP 及 `collect` 路径仍沿用原配置，没有因为本次诊断就自动切换为新的 HTTP 采集路径。
